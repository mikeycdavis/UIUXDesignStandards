## What

Plan section 13. Version-identity enforcement hardening and a `workflow_call` workflow that checks
this repository out at an immutable ref and runs the classifier and the gate against a consumer.

## Why

A consumer that pins a tag has pinned something mutable. The sha is the guarantee, and the workflow
is where that is made the documented default.

## Notes

Actionable as soon as v1.0.0 is tagged, because it needs an immutable ref to pin. Also carries the
open question of protected-tag policy, which is a host-configuration act outside the repository.

## Notes

Built after v1.0.0 was published, which is what made an immutable ref exist to pin.

The plan's own specification for this item was wrong and was not followed. It called for comparing
`policy.standardVersion` against the checked-out `VERSION`, which is what EngineeringStandards does —
and under ADR 0015 that comparison passes a post-release branch, because `VERSION` names the last
release and stays there during development. Identity is established against the artifact instead:
declared version equals executing version AND the executing tree is that release's tree.

The guard's first act was to refuse this repository, then the test suite. Both were correct; the
resolutions are `SELF_EVALUATION` by path containment, and a library-only waiver that suppresses the
refusal without suppressing the finding.

The external-consumer proof splits, because no honest ref today can both expose the new workflow and
produce a MATCH for a released version. **13A** — an external repository invoking the workflow pinned
to a development sha, whose correct result is a refusal — is tracked here. **13B**, the first
successful consumption of the workflow as an immutable release, is [ST-01](ST-01.md) and is blocked
on v2.0.0 (ADR 0017).
